Your routine is reasonable if `_sun_position` and `_moon_position` return accurate, matching ecliptic longitudes. The main limitation is that `angle = lm - ls` is a **longitude difference**, while your illumination calculation treats it as the angle between the Sun and Moon as seen from Earth. Those angles are close, but not identical because the Moon travels above and below the ecliptic.

For the phase angle, keep the longitude difference: the US Naval Observatory defines the primary phases using the Moon’s apparent ecliptic longitude minus the Sun’s. For illumination, calculate the Moon–Sun angular separation using both objects’ ecliptic latitude and longitude. [USNO phase definitions](https://aa.usno.navy.mil/faq/moon_phases)

```cpp
const double dLon = (lm - ls) * DEG_TO_RAD;

// and the Sun latitude is treated as zero:
const double betaMoon = moonLatitudeDeg * DEG_TO_RAD;

const double cosElongation =
    std::clamp(std::cos(betaMoon) * std::cos(dLon), -1.0, 1.0);

const double elongation = std::acos(cosElongation);

// This is a useful approximation to the illuminated fraction:
const double amountLit = (1.0 - cosElongation) / 2.0;
```

That improves the illumination estimate, but for a more physically accurate fraction, calculate the **phase angle at the Moon** from the Sun–Earth–Moon triangle, using Sun–Earth, Earth–Moon, and Sun–Moon distances. Then use `(1 + cos(phaseAngle)) / 2`. USNO describes its illuminated fraction as a geocentric quantity. [USNO illuminated fraction](https://aa.usno.navy.mil/data/MoonFraction)

There’s a definite accuracy problem in `_Julian`: `c` and `e` are integers, so their fractional day contributions are discarded. That can shift the date by close to a day—far more than the smaller errors in the Sun and Moon position formulas.

Replace `_Julian` with this version. It keeps the Gregorian reform handling but uses `double` values and `floor` for the calendar terms:

```cpp
static double _Julian(int32_t year, int32_t month, double day)
{
    int32_t a = year;
    int32_t m = month;

    if (m < 1 || m > 12)
        return std::numeric_limits<double>::quiet_NaN();

    if (m <= 2)
    {
        --a;
        m += 12;
    }

    double b = 0.0;

    // Gregorian calendar began on 1582-10-15.
    const bool gregorian =
        a > 1582 ||
        (a == 1582 && m > 10) ||
        (a == 1582 && m == 10 && day >= 15.0);

    if (gregorian)
    {
        const double century = std::floor(a / 100.0);
        b = 2.0 - century + std::floor(century / 4.0);
    }

    const double c = std::floor(365.25 * (a + 4716));
    const double e = std::floor(30.6001 * (m + 1));

    return b + c + e + day - 1524.5;
}
```

This is the standard Julian Date form. The current code’s constant and year handling are also inconsistent with that form, so the replacement should be used together with your existing subtraction of `2444238.5`.

```cpp
static double wrap360(double deg)
{
    deg = std::fmod(deg, 360.0);
    return (deg < 0.0) ? deg + 360.0 : deg;
}

static double _sun_position(const double &j)
{
    // j is days from JD 2444238.5, the epoch used by _getPhase().
    const double jd = j + 2444238.5;
    const double T = (jd - 2451545.0) / 36525.0;

    const double L0 = wrap360(
        280.46646 + T * (36000.76983 + 0.0003032 * T));

    const double M = wrap360(
        357.52911 + T * (35999.05029 - 0.0001537 * T));

    const double Mrad = M * DEG_TO_RAD;

    const double C =
        (1.914602 - T * (0.004817 + 0.000014 * T)) * std::sin(Mrad)
        + (0.019993 - 0.000101 * T) * std::sin(2.0 * Mrad)
        + 0.000289 * std::sin(3.0 * Mrad);

    const double trueLongitude = L0 + C;
    const double omega = (125.04 - 1934.136 * T) * DEG_TO_RAD;

    // Apparent geocentric ecliptic longitude, degrees.
    return wrap360(trueLongitude - 0.00569 - 0.00478 * std::sin(omega));
}
```
